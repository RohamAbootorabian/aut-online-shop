# فروشگاه اینترنتی — فاز ۲

اصول طراحی نرم‌افزار · دکتر هانیه فلاح · پاییز ۱۴۰۵ · دانشگاه صنعتی امیرکبیر

یک فروشگاه اینترنتی خط فرمانی در جاوا، با لایه‌بندی `model / repository / service / cli`.
کد از فاز اول آمده و در این فاز **بر اساس اصول SOLID بازطراحی شده** و با شش نمودار UML
مستند شده است.

## معرفی پروژه

مشتری ثبت‌نام می‌کند، فهرست محصولات را می‌بیند و جست‌وجو و فیلتر و مرتب‌سازی می‌کند، سبد
می‌بندد، سفارش ثبت می‌کند، پرداخت می‌کند و نظر می‌گذارد. مدیر محصول و دسته‌بندی و موجودی را
مدیریت می‌کند. در مجموع ۳۶ داستان کاربری، که در فاز اول به ۱۵ Domain Story و ۱۰۹ فعالیت
تبدیل شده بودند.

سه تصمیم که کل طراحی را شکل داده‌اند:

- **قیمت در لحظهٔ افزودن به سبد قفل می‌شود.** `CartLine` یک کپی از قیمت نگه می‌دارد، نه یک
  اشاره به محصول. تغییر بعدی قیمت، سبد و سفارش گذشته را دست نمی‌زند.
- **پرداخت یک «تلاش» است، نه یک «نتیجه».** هر بار پرداخت یک `Payment` تازه می‌سازد. پرداخت
  ناموفق سفارش را قابل‌پرداخت نگه می‌دارد تا بشود دوباره تلاش کرد، و خودِ تلاش ناموفق هم
  حذف نمی‌شود.
- **غیرفعال کردن محصول، گذشته را خراب نمی‌کند.** محصول از فهرست فروش می‌رود ولی سفارش‌های
  قبلی و نام محصول درونشان سر جایشان می‌مانند.

## اجرا

نیاز: جاوا ۱۷ یا بالاتر، و Maven.

```sh
cd online-shop
mvn compile
mvn exec:java
```

مدیر نمونه برای ورود: `admin@shop.ir` / `admin123`
فروشگاه با دو دسته‌بندی و چهار محصول پر می‌شود تا بشود بدون تایپ کردن کل مسیر را رفت.

## تست

```sh
mvn test
```

**۶۵ تست.** هر تست نام داستان کاربری‌ای را که از آن آمده در `@DisplayName` دارد، پس شکستن
یک قانون مستقیم به نیازمندی‌اش اشاره می‌کند.

> `-ea` در `pom.xml` روشن است، یعنی `checkRep()` در تست‌ها **واقعاً اجرا می‌شود**. بدون آن،
> `assert` در جاوا بی‌صدا نادیده گرفته می‌شود.

### قاعدهٔ وابستگی

| لایه | به چه چیزی وابسته است |
|---|---|
| `model` | **به هیچ‌چیز** |
| `repository` | فقط `model` |
| `service` | `model` و **رابط‌های** `repository` — نه پیاده‌سازی‌شان |
| `repository.memory` | `model` و رابط‌های `repository` |
| `cli` | `service` و `model` |
| `Main` | به همه — و تنها جایی است که پیاده‌سازی‌ها را انتخاب می‌کند |

این ادعا نیست، قابل بررسی است — هر پنج دستور باید **هیچ** چیزی برنگردانند:

```sh
grep -rl 'import ir.aut.shop.\(service\|cli\|repository\)' src/main/java/ir/aut/shop/model/
grep -rl 'import ir.aut.shop.cli'                          src/main/java/ir/aut/shop/service/
grep -rl 'repository.memory'                               src/main/java/ir/aut/shop/service/
grep -rn 'public [A-Z][A-Za-z]*Service(.*Map<'             src/main/java/
grep -rl 'System.out' src/main/java/ir/aut/shop --exclude-dir=cli
```

## روند کار با Git

```
main                      نسخه‌های پایدار
└── develop               یکپارچه‌سازی
    ├── member-1          شاخهٔ شخصی عضو اول
    │   └── feature/…     هر قابلیت یک شاخه
    └── member-2          شاخهٔ شخصی عضو دوم
        └── feature/sequence-diagram-review
```

هیچ شاخهٔ `feature` مستقیم به `develop` یا `main` ادغام نمی‌شود. مسیر همیشه
`feature → شاخهٔ شخصی → develop → main` است، و ادغام در `develop` بعد از Code Review عضو
دیگر انجام می‌شود.

پیام‌های commit از الگوی `<type>: <short summary>` پیروی می‌کنند — انگلیسی، فعل امری،
حداکثر ۷۲ کاراکتر، و هر تغییر منطقی در یک commit جداگانه.

## چند تصمیم طراحی (از فاز اول)

**قانون دامنه در نوع، نه در شرطِ تکراری.** به‌جای تکرار «تعداد باید مثبت باشد» در هر متد،
`Quantity` خودش منفی و صفر را رد می‌کند. همین‌طور `Money` (نامنفی)، `StockCount` (نامنفی)،
`Rating` (۱ تا ۵)، `SearchPhrase`. یک Precondition تکرارشونده تبدیل به یک RI سطح نوع شد.

**`Order` فقط در `status` تغییر می‌کند.** قلم‌ها، آدرس و سه مبلغ بعد از ثبت `final` اند؛
سفارش یک سند تاریخی است.

**جلوگیری از Rep Exposure.** `Cart.lines()`، `User.addresses()` و `Product.imageUrls()` همه
`List.copyOf` برمی‌گردانند، نه ارجاع داخلی.
